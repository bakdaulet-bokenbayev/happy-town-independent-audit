# HT-11 · Session lifecycle documentation gaps

**Review date:** 20 November 2026  
**Audited revision:** `f23375fee54bae8942a1c23a702adb04ed6c99a2`  
**Disposition:** Potential audit observation for review

The tracked `README.md:48–54` explains Auth.js Credentials, session identity fields, server-side authorization and audit logging. The audit materials describe JWT configuration and a verification objective. The reviewed repository and audit material do not contain a maintained application session lifecycle policy covering the items below. Private material outside those locations was outside this review. [Audit overview](../../../../methodology/application-overview.md) · [HT-11 test plan](../../../../methodology/test-plan.md#ht-11--session-replacement-on-authentication) · [Prior documentation inventory](../interim-20261120T164431Z/documentation-inventory.md)

| Missing material | Why it matters | Evidence that would close the gap |
| --- | --- | --- |
| Documented re-authentication transitions | `app/login/page.tsx:8–11` redirects existing sessions. The backend Credentials branch can still authenticate successfully. Without a lifecycle specification, a reviewer cannot tell when the product intends to ask again for credentials or treat a sign-in as replacing the current session. | A maintained transition table for initial sign-in, in-session credential verification, ordinary renewal and separately initiated sign-in. Identify the intended behavior by role where it differs. |
| Replacement and server-side invalidation contract | `auth.ts:14–64` configures JWT issuance and identity mapping. `lib/auth/authorization.ts:9–38` defines account and role checks. Neither the README nor the audit design reference specifies when replacement takes effect, which existing session it affects or what the server should do if invalidation fails. | An approved lifecycle design defining who or what can terminate the current session, when it becomes unusable, what validation enforces and how the application handles failure. |
| Lifetime, renewal and parallel-session policy | `auth.ts:18` configures eight hours, and `node_modules/@auth/core/lib/actions/session.js:33–51` can issue renewed expiry. The reviewed documents do not define inactivity, absolute lifetime, or intended behavior across independent sessions and devices. | A policy that states the intended time limits, renewal rules and any permitted parallel sessions, with rationale and a distinction between renewal and re-authentication. ASVS 7.1.1 and 7.1.2 are Level 2 and would need separate scope approval before scoring. |
| Session lifecycle verification and audit evidence procedure | `README.md:50–54` states that authentication events are logged. `auth.ts:66–68` records a login outcome, while the existing test suite has no lifecycle regression assertion. The material does not establish which evidence demonstrates replacement and invalidation independently of a successful login. | A maintained verification procedure with approved synthetic fixtures, expected backend state or decisions and redacted evidence requirements for issuance, termination and post-transition access. |

**Suggested observation wording.** Happy Town documents its authentication mechanism and role checks. The material examined does not define session replacement and revocation behavior or a procedure to verify that behavior. A maintained session lifecycle policy would give development and audit teams a common basis for implementation acceptance and regression coverage.

V7.2.4 assesses technical issuance and termination. It does not itself require a policy document. This documentation observation has no assigned severity or canonical finding ID. The separate technical assessment traces the implementation and does not use absence of documentation as proof of a defect.
