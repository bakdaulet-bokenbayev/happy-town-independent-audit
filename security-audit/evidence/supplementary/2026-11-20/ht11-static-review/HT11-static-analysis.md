# HT-11 · Static analysis of session replacement

**Review date:** 20 November 2026  
**Audited revision:** `f23375fee54bae8942a1c23a702adb04ed6c99a2`  
**Criterion:** OWASP ASVS `v5.0.0-7.2.4`, Level 1

> Verify that the application generates a new session token on user authentication, including re-authentication, and terminates the current session token.

[OWASP ASVS 5.0.0, V7.2 Fundamental Session Management Security](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x16-V7-Session-Management.md#v72-fundamental-session-management-security)

**Recommendation for review: FAIL based on source.** A successful Credentials authentication creates a fresh JWT. The same transition neither revokes the current JWT nor changes the account state used to authorize it. The protected access path verifies the JWT and the account but has no condition that rejects an otherwise-valid JWT because a later authentication superseded it. This conclusion describes the audited implementation. No runtime reuse or HTTP status was observed in this review.

## Scope and provenance

The application and the installed Auth.js dependency were read from the isolated audit worktree. The lockfile pins `next-auth` 5.0.0-beta.32 and `@auth/core` 0.41.3, and the installed package manifests agree. Source paths below are relative to that worktree. The review examined the app configuration, native Credentials handler, both app callbacks, the default decoder, local route guards, tracked schema and migrations, repository documentation and existing test sources. No application requests, browser actions, test executions or database connections were made.

## Implementation conclusions

| Is there a revocation mechanism for replaced sessions? | `auth.ts:55–61` maps `userId` and `role` into claims and projects them into the session. `lib/auth/authorization.ts:10–14` queries `id`, `status: "ACTIVE"` and `archivedAt: null`. `prisma/schema.prisma:169–205,809–825` defines account and audit-event data. The tracked schema and migrations expose no session registry, revocation list, token version or issue-time cutoff used by this flow. It checks token validity and the current account. It has no latest-session or replacement check. Additional record-level authorization still applies. This result does not depend on a policy that restricts separately created parallel sessions. |

## Protected route inventory

No tracked `middleware.ts` or `proxy.ts` centralizes auth in this revision. Protection is applied at the page and handler level. The public landing and login pages only use the session to decide where to route a visitor (`app/page.tsx:5–9`, `app/login/page.tsx:8–11`). The Auth.js catch-all is the authentication and session handler, with its own validation. Its session response does not run the app's fresh-account lookup in `getCurrentUser()`. It therefore cannot by itself demonstrate access to protected business data. The unrelated helpers in `app/chatgpt-auth.ts:21–48` have no tracked call sites outside their own file.

The protected inventory comprises 25 server pages, including ADMIN portal and development diagnostics, plus 12 business API route files with 19 explicitly exported methods. The parent and teacher layouts are additional guard locations. The installed dependency's separate sign-out action uses the JWT branch and clears the browser cookie (`node_modules/@auth/core/lib/actions/signout.js:9–29`). Logout remains the distinct HT-12 trigger in HT-F01. It neither supplies the missing re-authentication transition control nor establishes a new runtime finding here.

## Evidence boundary and disposition

This source review follows the complete authentication, issuance and authorization chain and identifies which state each step changes or reads. It supports a **FAIL recommendation for V7.2.4** at this revision because server-side termination is absent from that chain. It records no reuse of a live token and makes no claim of an observed unauthorized response. If the recommendation is accepted later, cross-reference HT-F01 for the shared revocation design while keeping the two different triggers traceable. The canonical Inconclusive result and findings register are unchanged in this working paper.
