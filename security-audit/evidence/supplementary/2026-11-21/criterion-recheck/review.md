## HT-07 follow-up

The original matrix called for comparing implemented defenses with the application's security documentation. Fieldwork traced the sign-in wiring and ran the limiter by itself with a simulated clock. That established the configured threshold, recovery, isolation and reset at the module boundary. The recheck loads the exact audited Git objects for the Credentials provider and limiter. The provider runs with an in-memory clock, user lookup, password comparison and audit event recorder. It produces no network requests or application audit events.

The expected component behaviors were denial before lookup for a limited fixture, failure recording for an unavailable account and a mismatched in-memory password result, reset upon successful verification, and recovery at the configured clock boundary. All five assertions passed. The separate public GET produced HTTP 200, HTML and a password input on the previously attested listener. It exercised page availability. The provider assertions record branch outcomes inside Node.js. The observed GET and the assertions have separate evidence IDs and neither supplies a live sign-in limiter response. [Provider test](ht07-provider.test.mjs) · [Terminal results](ht07-provider-results.txt) · [Public HTTP record](ht07-public-http.json)

The full criterion requires a governing security baseline for the audited configuration and representative sign-in integration evidence against it. The available documentation omits the settings, reset and lockout safeguards needed for that comparison. A dated, owner-approved specification applicable to the audited build and redacted integration observations measured against it would allow reassessment. Defining expected deployment behavior from the implementation alone would make the comparison circular.
